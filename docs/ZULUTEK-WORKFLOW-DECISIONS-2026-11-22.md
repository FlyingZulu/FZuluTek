# ZuluTek — décisions de workflow et points d'inspection (22 novembre 2026)

> Spécification validée en conversation. Ce document consigne des décisions de conception, **pas une preuve d'implémentation** sur APK ou FM-1. Les anciens documents peuvent décrire d'autres raccourcis. Ne pas les prendre comme autorité pour ces nouvelles décisions.

## Rituel de navigation

- Les gestes doivent être cohérents avec la famille fonctionnelle de leur bouton. Éviter d'ouvrir des pages sans rapport par double-tap.
- **HOME court** parcourt uniquement **BASSE → LEAD → DRUMS → BASSE**. Retirer LOOP de ce cycle.
- **REC + SEQ** ouvre **LOOP**.
- **REC + EDIT** ouvre **MACRO**.
- **EDIT court** ouvre/ferme la page **XY**. Fermer la page ne désactive pas XY HOLD ni les effets.
- **EDIT long (~0,8 s)** active/désactive l'édition des pas **uniquement si une page de séquenceur Zulu est déjà ouverte** (DRUMS ou LOOPER, ONE SHOT / LOOP). Hors d'une page de séquenceur, EDIT long ne déclenche pas l'édition et ne navigue pas. EDIT fixe en édition, clignotant sur page XY. Priorité LED en cas de chevauchement à préciser.
- En édition des pas : 16 pas sélectionnables ; K1–K4 éditent quatre paramètres ; SELECT change la page de quatre paramètres ; changer de pas conserve la page de paramètres ; EDIT court quitte l'édition.
- **Nouvelle extension ARP/ATEK303** : lorsque la page de l'arpégiateur est déjà ouverte, **EDIT long (~0,8 s)** ouvre également une édition des pas sur le clavier (sans changer le moteur acid). Les 16 touches représentent/sélectionnent les 16 pas de la page ; **un appui sur OP1, OP2, OP3 ou OP4 choisit directement la page d'édition** : OP1 = pas 1–16, OP2 = 17–32, OP3 = 33–48, OP4 = 49–64. Pendant la lecture, leurs LEDs indiquent aussi la page actuellement jouée ; **le défilement de lecture ne change pas la page d'édition sélectionnée**. K1–K4 éditent les paramètres de la page courante ; SELECT parcourt les groupes de quatre paramètres ; EDIT court quitte. Distinguer visuellement la page sélectionnée pour l'édition de la page en cours de lecture, si elles divergent. **À vérifier** : mapping exact des paramètres acid, gestion des LEDs, conflits éventuels des OP1–OP4 avec d'autres usages et fonctionnement si pattern de moins de 64 pas.
- **SEQ seul** conserve son rôle de demande/génération de nouveau pattern acid ATEK303, avec nouveau timing d'application défini plus bas.
- **ARP seul** conserve sa fonction ATEK303.
- **REC + ARP** ouvre l'éditeur avancé acid **SEQ+**, sans régénérer le pattern courant.
- **REC + double-tap ARP** ouvre l'éditeur de notes pas à pas original ATEK303. Exception cohérente car toujours dans la famille ARP ; vérifier la reconnaissance single/double.
- **GLO court** ouvre le menu **GLOBAL** (nouveau nom de l'ancien OPTIONS).
- **GLO double-tap** : **aucune affectation confirmée** ; les anciennes mentions DRUMS/MACRO sont contradictoires et ne sont pas retenues.
- **GLO triple-tap** : raccourci ONE SHOT / pads / sirène rappelé par l'utilisateur ; **à confirmer dans le code** avant toute modification.
- **REC + GLO** : procédure d'enregistrement LOOP (documentée, à vérifier).
- **HOME + GLO** : redo (documenté, à vérifier).
- **REC + OCT−** : entrée/sortie du mode ASSIGN global (documenté, à vérifier).

## Tempo indépendant de l'arpégiateur ATEK303

- Conserver le réglage **TEMPO** de la page **SEQ**, sur **K3** (ordre documenté : K1 STEPS, K2 SCALE, K3 TEMPO, K4 ROOT).
- **K3 = 0** signifie **GLOBAL** : le séquenceur/arpégiateur ATEK303 suit le tempo général de ZuluTek. Ce n'est ni 0 BPM ni STOP.
- **K3 > 0** : tempo propre à l'arpégiateur, indépendant du tempo global. Exemple demandé : arpégiateur 280 BPM alors que ZuluTek est à 75 BPM.
- Revenir à **0 / GLOBAL** réactive la synchronisation sur le tempo global, **avec une zone tampon de 4 crans d'encodeur entre le BPM indépendant minimum et GLOBAL** afin d'éviter un basculement accidentel. Dans la zone tampon, conserver le BPM minimum sans changement de mode ; prévoir également une séparation perceptible dans le sens GLOBAL → tempo libre. **4 crans validés par l'utilisateur.**
- À inspecter : plage réelle de BPM disponible, mécanisme de synchronisation/rephase lors du retour à GLOBAL et persistance du réglage.

## GLOBAL et changement de pattern SEQ

- GLOBAL rassemble les réglages peu fréquemment modifiés : ECO, tempéraments/accordages, préférences système et autres paramètres globaux. Ne pas créer un second menu « Options ».
- Ajouter **SEQ CHANGE** dans GLOBAL :
  - **IMMEDIATE** (défaut) : demande et application immédiates, sans attendre la mesure/la boucle ;
  - **NEXT BAR** : application à la prochaine mesure ;
  - **+2 BARS** : application deux mesures plus tard.
- L'appui SEQ demande/génère le nouveau pattern immédiatement ; seule son application est différée selon le réglage. Ne pas redémarrer le transport. Vérifier dans le moteur acid le traitement des événements déjà en cours et la définition exacte de +2 BARS.

## ASSIGN global et MIDI

- ASSIGN reste actif lors des changements de pages ; sélectionner une source (contrôle physique, XY X/Y, modulateur, MIDI), confirmer via SELECT OUI/NON, puis ajouter des destinations au panier avec Shift et confirmation SELECT. Quitter ASSIGN ne supprime pas les affectations ; sauvegarde via KIT.
- Modes MIDI envisagés : INTERNAL, MIDI OUT CC, MIDI OUT NOTE, MIDI OUT NOTE + CC, MIDI IN, MIDI LEARN, MIDI TEACH. Vérifier l'interface exacte.
- Chaque source assignable possède jusqu'à **trois slots MIDI CC** configurables séparément : canal 1–16, numéro CC 0–127, courbe normale/inversée. Un slot vide n'émet rien.
- En ASSIGN, **OP1 / OP2 / OP3** activent ou désactivent les slots correspondants ; LED allumée = slot actif. Un seul slot actif facilite MIDI Learn ; plusieurs slots actifs peuvent émettre ensemble ; aucun slot actif = aucun CC externe.
- **OPn maintenu + potentiomètre** permet de piloter exclusivement le CC du slot n sans modifier le paramètre interne du potentiomètre. Vérifier la coexistence des gestes maintien et bascule, ainsi que le contexte hors ASSIGN avant implémentation.
- MIDI OUT NOTE + CC réutilise les configurations NOTE et CC existantes. Configurations et états des slots persistés dans KIT.

## Idée différée — MACRO

- Explorer plus tard la possibilité de **segmenter virtuellement la course d'un encodeur en zones** (par exemple premier quart affecté à une fonction MACRO). Idée seulement évoquée, **aucun comportement ni mapping validé** à ce stade ; reprendre lors de l'inspection MACRO.

## PoW! — punch-in, inspirations et contraintes de conception (visite du 23 novembre 2026)

- **Intention confirmée** : effets punch-in immédiats et expressifs, inspirés notamment des Pocket Operator (PO-12 Rhythm) et d'Amenity sur FM-1 ; priorité musicale aux **altérations rythmiques / glitchs temporels** : shuffle, BPM stutter, beat repeat, micro-décalages, granulaire, déplacements dans le temps. Garder aussi des filtres, delays, saturations et traitements de timbre.
- **Contrôle souhaité** : déclencher l'effet par maintien d'une touche et pouvoir **tourner K1–K4 pendant le maintien** pour régler en direct **quatre paramètres propres à chaque effet**. Modalités précises de sélection des effets, de mémorisation des paramètres et de relâchement à définir ; ne pas les inventer.
- **Palette artistique privée de conception** : Aphex Twin, High Tone, MF DOOM, Tom Waits, Noisia (DnB), Skrillex (dubstep), Daft Punk, Boards of Canada, Radiohead, plus une famille glitchcore. Évoquer ces univers par les traitements et l'esthétique, **sans citer explicitement les artistes dans l'interface publique**.
- **Pistes non figées** : environ quatre effets par famille, soit un catalogue exploratoire d'environ 40 propositions, **pas** 40 effets définitivement approuvés ni 40 effets simultanés sur les 16 touches. Exemples à explorer : Shuffle Punch, BPM Stutter, Time Slip, Granular Scrub, Beat Repeat, Reverse Slice, Micro-Jitter, Time Stretch Glitch. Éviter les doublons et prioriser le plaisir de jeu.
- **Identité visuelle APK** : donner aux familles PoW! une couleur / signature graphique reconnaissable et une présentation des potentiomètres adaptée à leur personnalité, sans nuire à la lisibilité et sans noms d'artistes.
- **Performance** : concevoir d'abord pour une APK Android stable, compatible autant que possible avec des appareils récents et plus anciens ; effets économes en CPU et mémoire, tampons limités, éviter les allocations dans le fil audio. ECO est un soutien, **pas une excuse pour une version normale instable**. Le portage FM-1 sera évalué séparément, effet par effet, avec mesures et aménagements possibles. **Faisabilité FM-1 et performances Android non encore vérifiées**.
- **Point technique à inspecter plus tard** : moteurs et buffers audio disponibles, latence, polyphonie/voix, synchro BPM, charge maximale de plusieurs punch-in, impact ECO, faisabilité des traitements temporels. Les références artistiques et noms d'effets sont des pistes, pas des copies de traitements existants.

## Principe transversal — navigation bidirectionnelle des paramètres (23 novembre 2026)

- **Intention approuvée** : généraliser à toutes les parties pertinentes de ZuluTek le principe d'une **fenêtre de quatre paramètres K1–K4**, parcourable dans deux orientations via les encodeurs **PRESET et ALGORITHM** : par **ligne** (même paramètre sur quatre sources/voies) et par **colonne/tranche** (quatre paramètres successifs d'une même source). Vise à rendre les réglages accessibles sans multiplier les sous-pages.

Ne pas déclarer ces choix résolus.

## SNAP — capture sélective et morphing ZOU / LOU (23 novembre 2026)

- **REC + PLAY** entre en mode capture SNAP et en ressort après la session ; il ne faut pas confondre ce geste avec un déclenchement de lecture. En capture, choisir un slot de destination parmi **16 touches blanches** (huit physiques à gauche, huit à droite) puis **SHIFT confirme** ce slot.
- Ensuite, comme en ASSIGN, naviguer librement entre les pages, toucher/tourner un paramètre cible et **appuyer sur SHIFT pour capturer explicitement chaque paramètre** ; répéter autant que souhaité. **REC + PLAY** termine la capture. Préciser lors de l'inspection la valeur exacte mémorisée, le comportement d'un slot déjà rempli et l'indication de capture.
- Les slots sont initialement répartis **8 ZOU (gauche) / 8 LOU (droite)**, avec couleur distincte pour chaque camp dans l'APK. Ces groupes sont des **pôles de morphing**, pas des limites rigides de stockage.
- Le **potentiomètre de morphing reste disponible après la sortie du mode SNAP**. **OCT−** active/désactive le pôle ZOU ; **OCT+** active/désactive LOU (hors geste contextuel de réaffectation en capture, à préciser). Deux pôles actifs : interpolation ZOU ↔ LOU ; un seul actif : interpolation entre ce pôle et l'absence de contribution snapshot (« dry ») ; aucun actif : déplacement du potentiomètre sans effet, mais **réactivation applique immédiatement la position courante**, saut éventuel assumé.
- **Réaffectation d'appartenance** : pendant la capture, avant de quitter, possibilité d'affecter un slot physiquement situé dans l'un des groupes au **pôle opposé** (exemple utilisateur : OCT+ pour LOU puis sélection d'un slot situé de l'autre côté). Le slot prend la **couleur du groupe d'affectation** dans l'APK ; sur FM-1, faute de couleurs, **la touche du slot déplacé clignote** pour indiquer cette exception. Le geste exact de réaffectation, la priorité OCT+/OCT− dans le contexte SNAP, la gestion des groupes et les LEDs sont à préciser, sans inventer de raccourci.
- **Point à inspecter** : anciens documents mentionnent REC+SEL pour page SNAP, REC+PLAY pour capture ; vérifier les handlers existants, les 16 slots, le moteur de morphing, la persistance KIT/SNAP, la signification de « dry » et les interactions avec ASSIGN/automation. **Cette note est une spécification de la visite, pas une preuve d'implémentation.**

- **Concordance / conflit documentaire vérifié** dans `docs/ZULUTEK.md` : page SNAP ancienne **K1 = fader ZU↔LU**, **K2/K3 libres**, **K4 = FLY whammy ±12 demi-tons** (voir passages en tête de document et vers lignes 263–265). L'idée de Fly existe donc, mais **son rôle ancien ne correspond pas à la nouvelle intention**. Ne pas présenter l'ancien whammy comme validé pour la nouvelle ergonomie.

K4 doit être un **petit BPM looper / stutter** lié au morph ZU/LU, dont le caractère se transforme selon K1–K3, plutôt qu'un effet indépendant ou un simple réglage de vitesse. Conserver le morph principal comme commande distincte. Les détails de division rythmique, quantité, buffer audio vs répétition de valeurs de paramètres, synchronisation et faisabilité FM-1 restent à concevoir et tester ; ne pas inventer de comportement définitif.

Au moins un mode doit offrir un **stutter BPM relativement classique et immédiatement musical**, avec une légère signature Fly ; les autres modes peuvent modifier plus fortement le rythme, les rebonds et l'irrégularité en fonction de K2 ELASTIC et K3 CHAOS. Ne pas figer le nombre de modes ni leur DSP exact. La suggestion « K4 augmente l'intensité du stutter » reste une interprétation à valider.

À **REC+PLAY**, montrer **d'abord une icône appareil photo** pour annoncer l'entrée en mode capture. Animations courtes, non intrusives et lisibles sur APK comme sur l'affichage FM-1 (à adapter aux capacités matérielles). Un compteur sur la pellicule a été proposé par l'assistant, **non validé**.

## NO SNAP — retirer sélectivement des paramètres (23 novembre 2026)

- **Concept utilisateur** : **NO SNAP** est le mode inverse de SNAP. Après avoir sélectionné la destination/collection de capture, on parcourt les paramètres pour **retirer individuellement** ceux déjà photographiés, plutôt que vider/recréer le SNAP.
- **Entrée à retrouver** : l'utilisateur se souvient de SNAP/NO SNAP mais pas du raccourci exact ; propose à titre d'essai **un mouvement de l'encodeur SELECT** pour basculer en NO SNAP. **Ne pas considérer ce geste comme validé** ; rechercher une éventuelle implémentation antérieure.
- **Pictogramme souhaité** : **appareil photo barré** (« photo interdite », comme dans un musée), plus universel que la main qui refuse une photo. Garder un indicateur persistant discret du mode, dans la logique de SNAP.
- **APK** : les potentiomètres/paramètres déjà capturés doivent être **entourés ou surlignés**, pour choisir rapidement lesquels retirer. La relation à ZU/LOU doit être lisible.
- **FM-1** : quand on touche/bouge un potentiomètre capturé, afficher un **petit témoin lumineux** indiquant à la fois **qu'il est capturé** et **à quel pôle ZU/LOU il est affecté** ; couleur du pôle si matériellement disponible, sinon alternative de codage à définir après inspection matérielle. Si un même paramètre est dans plusieurs snaps/pôles, la représentation reste à préciser.
- Recherche documentaire ponctuelle dans `docs/ZULUTEK.md`, `docs/ZULUTEK-SEQ-PLUS.md` et ce journal : **aucune occurrence explicite NO SNAP trouvée**. Cela ne prouve pas l'absence dans le code.

## SNAP — retouche et duplication immédiate (23 novembre 2026)

- **Retouche d'un SNAP** : lorsqu'un paramètre est déjà photographié dans le SNAP courant, le modifier puis le **capturer à nouveau via SHIFT** met à jour **sa valeur mémorisée** sans effacer les autres paramètres de ce SNAP.
- **Duplication contextuelle rapide** : juste après avoir clos/sauvegardé une capture par **REC+PLAY** (« ranger l'appareil photo »), une **nouvelle pression rapide REC+PLAY** doit permettre de **réentrer directement avec le contenu du SNAP qui vient d'être enregistré**, puis **choisir un nouveau slot destination** afin de produire une **copie conforme** (mêmes paramètres et mêmes valeurs). L'utilisateur peut conserver la copie ou ne retoucher qu'un paramètre pour créer une variante, sans tout recapturer.
- **Détails à préciser avant codage** : fenêtre temporelle exacte de la réentrée rapide, distinction avec l'entrée SNAP ordinaire, étape exacte qui confirme l'écriture de la copie, comportement si le slot cible est occupé, annulation, et relation avec la copie miroir par double-tap déjà décrite dans l'ancienne documentation. La copie doit être indépendante du SNAP source.

- **Destination de duplication déjà occupée — décision utilisateur** : afficher immédiatement une **alerte visuelle de remplacement**. Fenêtre très courte d'environ **1 seconde** : **SHIFT = NON / annuler le remplacement** ; **absence d'action à l'expiration = confirmer automatiquement la copie et écraser le SNAP de destination**. Éviter une validation positive supplémentaire pour garder le geste rapide. Le détail du pictogramme et de l'indicateur de temps est à concevoir. **Attention** : cette validation par défaut est destructive ; proposition de l'assistant, non approuvée, d'un undo/restauration après écrasement. Vérifier également que SHIFT n'est pas ambigu avec son rôle normal de capture pendant cette fenêtre.

- **Clarification impérative utilisateur : avertissement NON BLOQUANT**. La fenêtre d'environ une seconde n'est **pas une modale** et **ne retient pas l'utilisateur** : il peut changer de page, jouer, naviguer et poursuivre toute autre action immédiatement. L'absence de veto SHIFT pendant le délai vaut confirmation, **y compris s'il est déjà parti ailleurs** ; à l'expiration, le contenu précédent du slot cible est effectivement écrasé par la copie. L'avertissement ne doit ni prendre le focus ni imposer un temps d'attente. À concevoir : la portée exacte de SHIFT=annuler pendant cette seconde sans intercepter de manière gênante ses usages dans les autres pages.

## KIT — entrée et duplication homogène avec SNAP (23 novembre 2026)

- **Utilisateur valide REC+SAVE** comme raccourci d'accès/enregistrement des KITS (cohérent avec l'ancienne documentation). Un KIT représente une **capture complète de l'état global** à la manière des Parts Elektron : synthés et réglages sélectionnés, état/échantillon chargé du looper, tempo, SNAP, affectations et paramètres globaux pertinents. Préciser les données audio embarquées vs références persistées et contraintes FM-1 au moment de l'implémentation.
- **Nouvelle intention validée** : offrir la **même duplication contextuelle rapide que SNAP**. Après sauvegarde/fermeture par REC+SAVE, réappuyer rapidement sur REC+SAVE pour reprendre le KIT juste enregistré, sélectionner un autre slot et en faire une **copie indépendante complète** ; ensuite pouvoir retoucher cette copie sans affecter la source. Le détail du geste final de confirmation de destination et du délai de réentrée reste à définir en cohérence avec SNAP.
- **Slot de destination occupé** : reprendre le **même avertissement non bloquant d'une seconde** que SNAP ; SHIFT durant cette seconde = annuler, sinon écrasement automatique du KIT cible, même si l'utilisateur navigue ailleurs. Ce comportement est destructif ; examiner l'undo possible, non approuvé à ce stade.
- **À réconcilier avec la spécification historique** : page KIT REC+SAVE, SAVE→slot→SAVE pour sauvegarder, tap pour charger, appui long pour effacer. La duplication contextuelle ne doit pas supprimer ces usages sans décision explicite.


- **Capacité KIT décidée** : **5 pages de 16 slots = 80 KITS**, au lieu des 16 kits de l'ancienne spécification. En page KIT, **OP1/OP2/OP3/OP4/OP5** sélectionnent directement les pages **1/2/3/4/5** ; les 16 touches blanches sélectionnent le slot dans la page courante. **Duplication vers n'importe quel slot de n'importe quelle page**, pas seulement le slot voisin ; les règles d'avertissement/annulation d'écrasement s'appliquent.
- **Vérification documentaire des conflits OP** : dans `docs/ZULUTEK.md` et `docs/ZULUTEK-SEQ-PLUS.md`, pas d'affectation OP1–OP5 spécifique à la page KIT trouvée ; l'ancien KIT n'avait qu'une page de 16. ## Navigation exclusive des pages, exception banque de performance (23 novembre 2026)

- **Précision utilisateur** : **un tap simple sur GLO suffit à fermer le menu GLOBAL déjà ouvert** ; il n'est pas nécessaire de refaire un maintien de 1 s pour le quitter. **Ouvrir une autre page ferme GLOBAL automatiquement**.

## Distinction fondamentale : vue affichée ≠ activation du module (23 novembre 2026)

- **Correction explicite de l'utilisateur** : la règle « une seule page à la fois » ne concerne **que l'affichage/la navigation visuelle**. **Quitter ou remplacer une page ne désactive jamais automatiquement le module ou la fonction qu'elle représente** : séquenceur, looper, effets, synthés, paramètres, etc. continuent selon leur état propre.
- Séparer dans l'architecture et le vocabulaire **(1) vue/page courante, (2) état actif/inactif des moteurs et fonctions, (3) overlay persistant de commandes de performance**. Les actions de contrôle peuvent changer les états, mais la navigation visuelle seule ne doit pas les changer.
- **Fermer l'overlay** retire sa couche d'accès/sa priorité sur les touches ; cela ne réinitialise pas les paramètres modifiés ni ne coupe automatiquement les modules. Les déclenchements de type *momentary/held* (p. ex. PoW!) doivent toutefois avoir une gestion explicite de relâchement de touche pour éviter de rester coincés si on ferme l'overlay en cours de maintien — comportement exact à spécifier.
- **Supersession/clarification** de la section précédente : « fermer GLOBAL en ouvrant une autre page » signifie **masquer/remplacer sa vue**, non désactiver les fonctions globales.

## Mode FUSION FM-1 ↔ ZuluTek APK / Zulu Control : état partagé, vues indépendantes (23 novembre 2026)

- **Vision utilisateur** : lorsque le **FM-1 matériel** et **ZuluTek APK** sont connectés en **mode FUSION**, ils deviennent fonctionnellement **un seul instrument étendu**, pouvant partager/étendre des capacités et des données. **Zulu Control** peut également servir de surface de monitoring/contrôle.
- **Exemple central** : rester sur la **page LOOPER du FM-1** tout en affichant sur le **smartphone la page ARP/SEQ** pour surveiller (et potentiellement contrôler) l'arpégiateur exécuté sur le FM-1. Inversement, chaque écran peut naviguer librement. **Ne jamais synchroniser automatiquement les pages affichées** entre appareils ; leur navigation est **indépendante**.
- **Principe d'architecture** : **état musical/moteurs partagés ou synchronisés, vues indépendantes et simultanées** ; le smartphone n'est pas un simple miroir du FM-1, mais une autre fenêtre sur le même système. L'affichage d'une page ne change pas à lui seul l'activation des moteurs (règle précédente).
- **À concevoir/valider** : transport/protocole et latence de communication, modèle d'autorité et synchronisation bidirectionnelle, arbitrage des éditions concurrentes, portée réelle des ressources étendues (moteurs, audio, stockage), état de connexion/déconnexion, sauvegarde des KITS/SNAPs et possibilité de monitoring sans prise de contrôle. **Vision de design, non implémentation existante**.

## Correction structurante — FUSION vs INDÉPENDANT sont des modes d'intégration, non des modes d'affichage (23 novembre 2026)

- **Correction explicite de l'utilisateur (supersède la nomenclature précédente)** : ne **pas** appeler « MIROIR » et « INDÉPENDANT » les deux modes de fonctionnement. Il existe deux **niveaux d'intégration** :
  1. **FUSION** : FM-1 et ZuluTek APK forment un **instrument augmenté** exploitant conjointement les capacités des **deux moteurs**. L'APK peut effectuer le **sampling lourd**, ajouter des **voix de synthèse** (l'utilisateur évoque **quatre voix** comme perspective), et permettre des **modulations croisées simplifiées** et d'autres échanges approfondis. Le smartphone ne doit pas se limiter à monitorer le FM-1. Dans ce mode, **le choix d'affichage est indépendant** : vue miroir précise du FM-1 enrichie de tactile, **ou** deux pages distinctes simultanément sur les deux appareils.
  2. **INDÉPENDANT** : deux **instruments distincts côte à côte**, chacun gardant son propre moteur et son état ; connexion limitée aux échanges **MIDI** (clock/synchronisation, notes, commandes/messages MIDI), **sans communication étendue ni mutualisation des moteurs/ressources**.
- **Axes orthogonaux à ne plus confondre** : (A) **niveau d'intégration des instruments** FUSION/INDÉPENDANT ; (B) **présentation des vues en FUSION** miroir tactile enrichi / vues différentes. La « synchronisation des écrans » ne définit donc pas FUSION à elle seule.
- **Statut** : architecture souhaitée ; nombre exact de voix, partage audio/sampling, protocole de transport et modulations croisées à étudier techniquement, **non vérifiés comme implémentés**.

- **Emplacement de réglage** : **GLOBAL → MIDI ROUTING** (nom proposé) car ce sont des réglages de configuration relativement stables, **pas des commandes de performance à modifier pendant le jeu**. Ils s'appliquent à **tous les contrôleurs MIDI**, dont le Wavy MONKEY, et pas uniquement au MONKEY.
- Le **canal contextuel/FOLLOW** évoqué pour MONKEY peut être configurable lui aussi ; en FUSION, préciser s'il suit la partie active sur APK ou FM-1. **À trancher** : valeurs par défaut exactes, possibilité de canal OFF/OMNI, routage multicanal, canaux partagés entre destinations (layer), conflit éventuel avec le canal 10 utilisé par l'effet DRM du MONKEY, persistance globale versus capture dans KIT.
- **Supersession** : CH1→BASSE, CH2→LEAD, CH3→DRUMS, CH4→SIRÈNE sont des **exemples de mapping initial**, pas des affectations définitives.

## GLOBAL → MIDI ROUTING — split clavier et plages de notes (23 novembre 2026)

- **Nouvelle demande utilisateur** : pouvoir assigner **le même canal MIDI à plusieurs parties** (ex. BASSE et LEAD) et répartir les notes selon leur hauteur, avec un **point de split librement réglable** sur le clavier. Exemple : notes graves → BASSE ; notes aiguës → LEAD, tout en recevant sur le même canal MIDI.
- **Proposition de conception** : compléter le routage GLOBAL par une **plage de notes MIDI min/max par partie** (ou un contrôle de split équivalent) ; les plages pourraient également se chevaucher pour créer des layers, **option proposée non encore confirmée par l'utilisateur**. Cette configuration s'applique aux claviers MIDI externes dont le Wavy MONKEY, sans dépendre du canal seul.
- **À définir** : représentation du split sur le petit écran FM-1 et sur l'APK, capture du point de split par une note jouée, limites et transposition, gestion de Note Off si routage modifié pendant une note tenue, stockage GLOBAL versus KIT. **Pas implémenté ni validé matériellement.**

## OCT− / OCT+ réaffectés aux pôles ZU/LU ; transposition via HOME (23 novembre 2026)

- **Précision utilisateur** : les pressions simples **OCT− et OCT+** sont dédiées respectivement aux pôles de morphing **ZU et LU** (activation/désactivation selon le contexte SNAP défini précédemment). Pour changer l'octave du clavier : **HOME + OCT− = −1 octave** et **HOME + OCT+ = +1 octave**. L'utilisateur dit « je crois que c'est ça » : convention très probable, à confirmer si nécessaire lors du test ergonomique.
- **Priorité des combinaisons** : HOME + OCT doit intercepter l'événement avant toute action OCT seule afin d'éviter de basculer un pôle pendant la transposition. Définir la répétition sur maintien et les limites d'octave ultérieurement.
- **Conflit à résoudre** : le geste historique **REC + OCT−** ouvre ASSIGN ; vérifier la priorité des combinaisons et l'accès à ASSIGN sans déclencher ZU.

## Protection anti-feedback SNAP — ne jamais capturer le pilotage SNAP (23 novembre 2026)

- **Décision explicite utilisateur** : **OCT− et OCT+**, dédiés à l'activation des pôles ZU/LU, **ne doivent jamais être enregistrés dans les SNAP**. Un SNAP ne doit pas prendre un snapshot de son propre état de contrôle ni créer de boucle de feedback SNAP → SNAP.
- **Règle générale de conception proposée** : exclure des paramètres capturables toute commande qui contrôle le moteur SNAP lui-même (activation ZU/LU, sélection/déclenchement d'un SNAP, capture, etc.). Éviter également les déclenchements indirects de SNAP par les assignations ou macros activées par un SNAP. Les paramètres **musicaux** contrôlés par le morphing restent capturables normalement.
- **Implémentation à définir** : distinguer les paramètres musicaux des commandes de pilotage SNAP dans le registre des paramètres ; filtrer à la capture **et** à l'application (y compris vieux KITS/assignations), détecter ou empêcher les cycles dans les routes de modulation/ASSIGN. **Pas implémenté à ce stade.**

## Capture SNAP : knob ZULU exclu, FLY optionnel en GLOBAL (23 novembre 2026)

- **Décision utilisateur** : en plus des boutons OCT− / OCT+ (pôles ZU/LU), le **knob ZULU** qui pilote le morphing est **toujours exclu** des paramètres enregistrables dans un SNAP : un SNAP ne doit pas mémoriser son propre contrôleur.
- **Décision utilisateur** : les paramètres **FLY** sont **exclus par défaut** de la capture SNAP, mais un réglage explicite dans **GLOBAL** peut les rendre capturables pour les usages créatifs. Proposition de libellé : **GLOBAL → SNAP → CAPTURE FLY : OFF / ON**, valeur initiale **OFF**.
- Même avec CAPTURE FLY=ON, maintenir les protections anti-récursion : aucun SNAP ne peut modifier le knob ZULU, les pôles ZU/LU, le déclenchement/la sélection de SNAP ni les commandes de capture. Autoriser seulement les **valeurs de paramètres FLY** et non les actions de pilotage du système SNAP. Distinguer la valeur du paramètre et ses effets indirects dans le moteur ; vérifier capture et application.
- **À préciser ultérieurement** : si changer CAPTURE FLY dans GLOBAL affecte seulement les nouvelles captures ou aussi la lecture de SNAP déjà enregistrés avec FLY ; proposition prudente : n'affecter que les nouvelles captures, avec protections anti-boucle permanentes.

## RECTIFICATION IMPORTANTE — nature exacte d'un SNAP (23 novembre 2026)

- **Correction explicite de l'utilisateur** : un **SNAP n'enregistre PAS de son, ni d'audio**. C'est une **mémoire sélective de l'état/valeur de commandes et paramètres à un instant donné**, comparable aux **scènes de l'Elektron Octatrack**. Dans ZuluTek, l'utilisateur choisit explicitement les paramètres à mémoriser, un par un, avec SHIFT en mode capture ; le knob ZULU sert ensuite au morphing des valeurs entre les pôles ZU et LU.
- **Ne plus écrire « SNAP capture le son »** : cette formulation est conceptuellement fausse. Parler de **capture de valeurs de paramètres**, et non de capture audio. Le son peut évoluer en conséquence, mais n'est pas le contenu enregistré.
- **Restrictions de capturabilité confirmées** : OCT−/OCT+ (contrôle des pôles) et knob ZULU (contrôle du morphing) **jamais capturables** ; valeurs de paramètres FLY **exclues par défaut**, capturables seulement si l'option GLOBAL est activée. Interdiction des boucles SNAP → contrôle SNAP, indépendamment de cette option.
- Cette rectification **prime sur toute formulation antérieure contradictoire** dans le journal et dans les échanges.

Explorer les autres pages sans figer leurs affectations trop tôt.

## MONKEY — modulation STRICTEMENT momentanée, sans écriture de paramètre (23 novembre 2026)

- **Décision explicite utilisateur** : la surface tactile de modulation du Wavy MONKEY sert uniquement à **tweaker/perturber temporairement** un paramètre musical (p. ex. cutoff BASSE/LEAD ou drive DRUMS), car le pad n'est pas assez précis pour régler une valeur durablement.
- **Appui/pression** : appliquer une contribution de modulation momentanée à la valeur courante du paramètre, sans modifier sa valeur de base ni le KIT/SNAP. **Relâchement** : retirer entièrement cette contribution et retrouver la valeur normalement produite **à cet instant** par les réglages, morphing SNAP, automation et autres modulations, pas une valeur de départ figée.
- **Règle de moteur** : distinguer valeur persistante de paramètre, modulations de fond, et modulation MONKEY éphémère ; ne pas écrire de CC MONKEY comme réglage permanent. Gérer le retour à zéro sur déconnexion/perte de signal, ainsi que l'arbitrage/clamp lorsque plusieurs modulations s'additionnent. Vérifier la courbe de pression et la signalisation du relâchement du MONKEY réel.
- Cette décision **remplace l'alternative « maintien de la dernière valeur »** précédemment envisagée : comportement momentané obligatoire pour le pad MONKEY.

## MONKEY PAD — réaffectation contextuelle via ASSIGN (23 novembre 2026)

- **Décision utilisateur** : conserver les **affectations par défaut** de la surface de modulation du MONKEY (BASSE/LEAD → cutoff, DRUMS → drive ; autres pages à préciser), tout en permettant à l'utilisateur de **réassigner librement le paramètre ciblé sur chaque page** via le mode **ASSIGN** déjà conçu.
- **Principe d'interface proposé** : sélectionner la source **MONKEY PAD** dans ASSIGN, naviguer jusqu'à la page concernée et désigner le paramètre cible avec le geste habituel de sélection/confirmation d'ASSIGN ; conserver une affectation par contexte musical. Ne pas créer un éditeur de routage séparé uniquement pour MONKEY.
- **Invariance impérative** : quelle que soit sa destination ASSIGN, la surface MONKEY reste une **modulation momentanée non destructive** : appui = perturbation temporaire ; relâchement/déconnexion = retrait de la contribution ; aucune écriture du réglage permanent, du SNAP ou du KIT.
- **À préciser** : destinations par défaut des autres pages, portée des mappings (GLOBAL versus KIT), interaction avec la destination MIDI active du MONKEY et la navigation distincte FM-1/APK en FUSION.

## Page MACROS — quatre macros multi-cibles et commande maîtresse (23 novembre 2026)

- **Description utilisateur** : page MACROS avec **quatre potards/macros**, chacun pouvant contrôler **plusieurs paramètres simultanément**. Chaque **lien macro → paramètre** a sa propre transformation, indépendante des autres liens du même potard : comportement type élastique/FLY et autres modes précédemment évoqués, plage/zone d'activation, sens normal ou inversé, valeurs min/max, réponse différente suivant la zone de course.
- **Cinquième potard « dictateur » / MASTER** : contrôle les quatre macros ensemble, inspiration revendiquée **Tornado (Sugar Bytes)** et **Transit (Baby Audio)**. Il orchestre les quatre macros tout en respectant les règles de transformation individuelles de chaque destination. Le détail de la relation MASTER ↔ positions manuelles des macros reste à définir.
- **Distinction importante** : transformations définies **par affectation de paramètre**, pas une unique courbe globale par potard. Exemples d'usage : cutoff BASSE progressif, drive DRUMS actif seulement dans une zone, reverb LEAD inversée.
- **À vérifier** : les quatre contrôles physiques K1–K4 du FM-1 versus la représentation/accès au cinquième contrôle MASTER ; nombre de cibles par macro ; catalogue exact des modes partagés avec FLY ; configuration via ASSIGN ; persistance KIT ; interactions SNAP et performances. **Conception, non implémentation confirmée.**

## Priorité gestuelle REC avant OCT (23 novembre 2026)

- **Précision explicite utilisateur** : la combinaison est pensée et exécutée dans l'ordre **REC d'abord, puis OCT−/OCT+**. ## Fenêtre de tolérance temporelle des combinaisons REC (23 novembre 2026)

- **Intention utilisateur** : les notations `REC + bouton` signifient **priorité fonctionnelle de REC**, sans exiger un timing parfait des doigts. Prévoir une petite tolérance sur les boutons à double rôle pour éviter que leur action simple ne parte si REC arrive quasiment en même temps.
- **Proposition technique, non validée par mesure** : fenêtre initiale de l'ordre de **20–30 ms**, à calibrer en test matériel/APK ; si REC est déjà tenu, traiter immédiatement `REC → bouton`. Si le bouton arrive un peu avant REC, différer uniquement **son action simple** pendant la fenêtre, puis déclencher soit le combo, soit le simple. Une fois combo reconnu, inhiber le simple aussi au relâchement. Pas de déclenchement spéculatif puis annulation.
- **Portée** : généraliser l'arbitrage aux boutons qui ont une interaction REC, **pas** à toutes les touches ni aux gestes musicaux à latence critique. Examiner le debounce matériel, le scan des touches, la latence et les interactions avec HOME/long/double appui ; l'utilisateur doit connaître la tolérance choisie.

## Arbitrage utilisateur — tolérance REC fixée à 20 ms (23 novembre 2026)

- **Décision** : fenêtre de reconnaissance des appuis quasi simultanés **20 ms maximum**, et non 20–30 ms. Le musicien privilégie la réactivité ; ne pas augmenter sans observation concrète lors des essais.
- Si REC est déjà enfoncé : déclenchement immédiat de la combinaison, sans délai ajouté. Sinon, seuls les boutons à action simple et combinaison REC peuvent différer leur action simple de **20 ms au plus** pour détecter REC. Jamais de double déclenchement simple+combo, y compris au relâchement.
- Valeur de design actée ; implémentation et validation sur matériel/APK restent à faire.

## MACROS — Dictateur inspiré de Turnado et Transit (23 novembre 2026)

- **Demande utilisateur** : le cinquième contrôle MASTER des quatre MACROS doit avoir plusieurs comportements, dont une course séquençable, et permettre **quatre courbes/trajectoires différentes** entre la position du MASTER et chaque macro. L'utilisateur préfère configurer les **modes** dans GLOBAL. L'affectation du MASTER à un encodeur physique reste non décidée ; PRESET est réservé à ZULU.
- **Sources externes vérifiées** : Sugar Bytes **Turnado**, Dictator = un fader parcourt des points d'automation individuels sur huit pistes (https://downloads.sugar-bytes.de/manuals/Turnado_Auria.pdf) ; Baby Audio **Transit 2**, plages inversables et pentes individuelles, modes Macro/LFO/Follower/Sidechain/Gate/Sequencer (https://babyaud.io/docs/transit-2-manual).

Le MASTER entraîne les quatre macros, puis chaque macro transforme ses destinations par ses propres zones/courbes.
- **Proposition d'emplacement** : `GLOBAL > MACRO MASTER` pour mode de déplacement, sync BPM, direction, bouclage, déclenchement ; **éditeur MACROS** pour dessiner les quatre trajectoires propres au KIT/mapping, afin que GLOBAL ne fige pas les chorégraphies de tous les morceaux. Persistance et priorité MASTER vs manipulation directe des K1–K4 vs SNAP à définir ; aucune implémentation affirmée.

## Dictateur MACROS piloté par l'arpégiateur BASSE ou LEAD (23 novembre 2026)

- **Nouvelle demande utilisateur** : prévoir un mode où le parcours du MASTER/Dictateur est **corrélé au motif de l'arpégiateur BASSE ou LEAD**, et non simplement calé au même BPM. L'utilisateur demande la faisabilité ; aucune implémentation n'est encore vérifiée.
- **Proposition** : `GLOBAL > MACRO MASTER` : SOURCE = BASSE ARP / LEAD ARP ; MODE = STEP (pas d'arpège → indice/position d'une séquence), PITCH (hauteur de note → position normalisée), VELOCITY (vélocité/accent → position), avec SMOOTH optionnel entre positions. Les quatre trajectoires MASTER→M1..M4 restent indépendantes.
- **Faisabilité conditionnelle** : utiliser les événements **note-on/pas/accent émis par le moteur d'arpège** avant sortie MIDI/audio, sans analyse sonore ni DSP lourd. Vérifier si BASSE et LEAD possèdent réellement des instances/flux d'événements distincts dans l'architecture actuelle, le routage, le traitement des silences/rests, la normalisation de pitch, la synchro, et les conflits d'automation SNAP/MACRO. Ne pas déclarer le mode fonctionnel sans inspection et tests.

## Proposition de 10 modes de parcours du Dictateur (23 novembre 2026)

- L'utilisateur souhaite environ **dix modes**, notamment un mode de type **ARROW**, inspirés de l'écosystème Sugar Bytes/Turnado, pour animer la course MASTER des quatre MACROS. **Sélection proposée, non encore validée** : 1 ARROW (avant bouclé), 2 REVERSE (arrière bouclé), 3 PING-PONG (aller-retour continu), 4 ZIGZAG (aller-retour par pas), 5 RANDOM (positions aléatoires quantifiées), 6 DRUNK (marche aléatoire à petits pas), 7 WAVE (balayage continu), 8 STEP SEQ (positions programmables), 9 ARP BASS (motif de l'arpégiateur BASSE), 10 ARP LEAD (motif de l'arpégiateur LEAD).
- **Précision de provenance** : le Dictator de **Turnado** est documenté comme un fader parcourant les points d'automation de huit pistes ; les directions à flèches Forward/Backward/Ping-Pong/Inverse Ping-Pong/Random ont été retrouvées explicitement dans le manuel **Sugar Bytes Unique**, et non prouvées comme dix modes officiels de Turnado. Sources : https://downloads.sugar-bytes.de/manuals/Turnado_iPad.pdf et https://downloads.sugar-bytes.de/manuals/Unique.pdf .
- Ces modes pilotent la **position du MASTER** ; les quatre courbes MASTER→M1..M4 restent indépendantes. La place du mode MANUAL, les variantes ARP STEP/PITCH/VELOCITY, la synchronisation et le coût embarqué sont à préciser.

## Décision utilisateur — MACROS comme widget persistant et affectation physique (23 novembre 2026)

- **Décision de conception** : MACROS doit se comporter comme un **widget superposé aux autres pages**, à l'image du widget SIRÈNE déjà envisagé. Lorsqu'on l'active, il prend temporairement la main sur les six encodeurs **K1, K2, K3, K4, SELECT, ALGORITHM**, indépendamment de la page affichée.
- **Affectation décidée** : **K1–K4 = quatre macros individuelles** ; **SELECT = DICTATEUR/MASTER** pilotant les quatre macros via leurs trajectoires indépendantes ; **ALGORITHM = choix de la forme/du mode de parcours du Dictateur** (inspirations Turnado et Transit, propositions ARROW, PING-PONG, etc., et **ARP STEP / ARP PITCH / ARP VELOCITY**). **PRESET reste exclusivement le ZULU morph permanent**, OCT−/OCT+ restent les pôles ZU/LU : ces trois commandes ne sont pas empruntées par le widget.
- **Proposition complémentaire non encore validée** : source arpégiateur BASSE/LEAD sélectionnée dans `GLOBAL > MACRO MASTER`, plutôt que deux modes séparés pour chaque source.
- **Point d'ergonomie à trancher** : distinction entre **widget affiché/possédant les six encodeurs** et **moteur MACROS actif en arrière-plan** ; recommandation de rendre les commandes à la page lorsque la superposition est fermée, sans arrêter les macros. Définir le geste d'ouverture/fermeture et l'arbitrage avec widget SIRÈNE, autres overlays et commandes contextuelles ; ne pas déclarer ces interactions déjà implémentées.

## Bibliothèque réutilisable de comportements de knobs et éditeur tactile (23 novembre 2026)

- **Demande utilisateur** : pouvoir dessiner librement le motif/la course du Dictateur à la manière de Turnado, dans un éditeur **tactile**, accessible via **GLOBAL** ; enregistrer ces courses dans une **bibliothèque de comportements de knobs** et les réaffecter ultérieurement à d'autres boutons/paramètres, pas seulement aux MACROS.
- **Architecture proposée à valider** : séparer (1) **forme de course** réutilisable (points, plateaux, sauts, inversions, interpolation), (2) **mode de lecture** de cette course (MANUAL, ARROW, REVERSE, PING-PONG, RANDOM, DRUNK, WAVE, STEP SEQ, ARP STEP/PITCH/VELOCITY), et (3) **affectation** vers un contrôle/paramètre avec plage, profondeur et inversion propres. `GLOBAL > CURVE LIBRARY` pour dessiner/nommer/sauvegarder, `GLOBAL > MACRO MASTER` pour choisir et jouer un profil. L'éditeur tactile se ferait sur **APK/écran tactile connecté**, le FM-1 physique n'ayant pas d'écran tactile ; accès/choix des profils sur FM-1 à spécifier.
- **Précautions proposées, non validées** : distinguer **copie indépendante** d'un profil et **lien partagé** pour éviter de modifier involontairement d'autres affectations ; définir stockage/versions, résolution et interpolation, priorité entre macro directe/Dictateur/SNAP/automations, et garde-fous contre boucles de modulation. Les paramètres capturables SNAP ne doivent pas permettre de contrôler directement les pôles ou le knob ZULU.
- **Statut** : concept utilisateur accepté comme axe de conception ; architecture et UX détaillées proposées, aucune implémentation confirmée.

## Clarification utilisateur — séquences Dictateur ≠ bibliothèque universelle de courbes (23 novembre 2026)

- **Décision clarifiée** : les **motifs/séquences à quatre pistes** du Dictateur (M1–M4, tête de lecture commune, dessin tactile) sont **propres au widget MACROS** et n'ont pas vocation à être réutilisés tels quels pour les autres boutons. Ne pas les confondre avec les profils de courbes.
- **Idée validée avec enthousiasme** : une **bibliothèque indépendante de courbes de réponse / formes de mouvement individuelles**, dessinables au doigt, nommables, sauvegardables et réutilisables sur d'autres contrôles ou paramètres compatibles dans ZuluTek. Elle peut également servir aux MACROS, sans que leurs séquences à quatre pistes deviennent des profils universels.
- **Emplacement voulu** : création/édition tactile via l'APK dans GLOBAL ; persistance, formats et interface de sélection FM-1 restent à spécifier.

## Décision — ALGORITHM : dix slots de comportements Dictateur (23 novembre 2026)

- **Décision utilisateur** : l'encodeur physique **ALGORITHM** du widget MACROS propose **exactement 10 positions/slots**, pas une longue liste de dizaines de modes. Chaque slot charge un **comportement du Dictateur**, avec des profils d'usine prêts à l'emploi et possibilité de charger/sauvegarder des profils utilisateur.
- Le **Dictateur conserve son propre petit séquenceur à quatre pistes M1–M4**, avec des motifs et des règles de lecture propres à MACROS. Il **n'utilise pas la bibliothèque générique de courbes** comme architecture de ses motifs. La **bibliothèque de courbes dessinables et réutilisables pour les autres potards/paramètres** demeure une fonctionnalité distincte, approuvée.
- **Affectations d'usine suggérées (non encore validées une par une)** : 01 ARROW, 02 REVERSE, 03 PING-PONG, 04 ZIGZAG, 05 RANDOM, 06 DRUNK, 07 WAVE, 08 ARP STEP, 09 ARP PITCH, 10 ARP VELOCITY. Un slot utilisateur peut remplacer le profil chargé dans un emplacement, sans effacer l'usine ; définir mécanisme de sauvegarde/chargement et si les 10 emplacements sont par KIT ou globaux.
- SELECT reste le Dictateur physique ; K1–K4 les quatre macros ; PRESET le morph ZULU permanent. Distinction profil de parcours / contenu des quatre pistes à préciser dans l'éditeur, sans mélanger avec la bibliothèque universelle.

## Décision — ARP STEP / PITCH / VELOCITY comme sources de modulation universelles (23 novembre 2026)

- **Décision utilisateur** : les trois comportements **ARP STEP**, **ARP PITCH** et **ARP VELOCITY** restent utilisables par le Dictateur, **mais deviennent aussi des sources assignables à n'importe quel paramètre compatible de ZuluTek**, à l'image de l'affectation des courbes de la bibliothèque.
- **Sens des sources** : STEP = progression/valeur/événement des pas d'arpégiateur ; PITCH = hauteur des notes arpégées ; VELOCITY = vélocité/accent des notes arpégées. Source **BASSE ou LEAD** sélectionnable par affectation. Une courbe de la bibliothèque peut transformer la réponse de chaque destination ; plage, profondeur, inversion et lissage par affectation.
- **Séparation préservée** : séquenceur multipiste propre au Dictateur ; sources ARP partagées ; courbes de réponse génériques réutilisables. Vérifier les événements réellement exposés par les arpégiateurs et définir arbitrage des modulations avant implémentation.

## Proposition ergonomique — ASSIGN comme point d'entrée unique (23 novembre 2026)

- L'utilisateur veut pouvoir assigner facilement **CURVES** et **ARP STEP/PITCH/VELOCITY** aux paramètres, depuis ASSIGN ou depuis la bibliothèque, sans parcours compliqué. Il n'a pas encore validé le geste exact.
- **Proposition à valider** : flux principal `REC + OCT−` (ASSIGN) → sélectionner/toucher la **destination** → choisir une **source de modulation** (ARP STEP/PITCH/VELOCITY, BASSE ou LEAD) et éventuellement une **courbe de réponse** → régler plage, intensité, inversion, lissage. Flux inverse sur APK : `GLOBAL > CURVE LIBRARY` → choisir courbe → `Assigner` → toucher destination ; les deux ouvrent une fiche ASSIGN commune.
- **Clarification conceptuelle** : une courbe de réponse seule ne génère pas nécessairement un mouvement autonome ; elle façonne une commande ou une source animée. Pour mouvement temporel autonome, prévoir source (LFO, ARP, séquenceur). Éviter un second moteur d'assignation.
- **À vérifier** : capacité réelle de détection de dernière destination touchée sur FM-1 et dans l'APK, conflits avec boutons REC et widget MACROS, accès aux paramètres non associés à un potentiomètre physique, retour visuel, sauvegarde par KIT ou GLOBAL. Aucune implémentation confirmée.
